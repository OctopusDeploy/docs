Decision document

Replacing the docs search

Three engines measured against the same 1,250 pages, through the same search overlay, on the same 102 queries. The legacy engine currently in production, and the two spikes built to replace it.

102 queries, 88 scored 876 searches per run 3 performance runs, medians reported Fast 4G, 4× CPU throttle Run 18 Aug 2026
Recommendation

Ship Orama.

It finds the right page in the top five more often than the engine it replaces (78% against 76%), and it is decisively better at the two things the legacy engine is worst at: natural-language questions (87% against 67%) and misspellings (58% against 42%). While you are still typing, it is better than both others by 14 points.

It also deletes 645 lines of hand-rolled stemmer, synonym table and ranking code that nobody wants to own.

The cost
A first search on a cold cache takes 5.7s on a mid-range phone on Fast 4G. That is the only gate it misses, and it misses it by a wide margin.
Why it is acceptable
The penalty lands once, on the first search of a first visit. Every subsequent search in that visit is 256ms, and a return visit is 201ms — both faster than legacy. Nothing loads at all for readers who never search.
Do this before shipping
Cut the cold path further. The index is still 5.33MB parsed and BODY_LIMIT is still 4,000 characters; there is real headroom left.

Correction

The premise this project started from was wrong

The replacement was justified on payload: the legacy index is 1.86MB. That is its uncompressed size. Your CDN serves it brotli-compressed, and on the wire it is 0.35MB — smaller than the Orama spike at 0.66MB, and beaten only by Pagefind at 0.08MB.

So payload is not a reason to replace the legacy engine, and it is a mild argument against Orama. The reasons that survive measurement are search quality and the 645 lines of hand-rolled search code. Both point the same way.

One payload number does still matter, and it is not the wire: the bytes that have to be parsed on every fresh page load, which no amount of caching removes.

Evidence — search quality

Does it find the right page?

Every query names the URLs that count as a hit, written against the live page list before any engine was run. Success@5 is the headline: the reader sees five rows without scrolling, so a hit inside five is a search that worked. MRR separates “missed it” from “found it, at rank seven”.

Full-length queries — 88 of 102 scored
Engine Success@5 Success@1 MRR Zero results
Legacy 76% 58% 0.671 8%
Pagefind 60% 38% 0.482 0%
Orama 78% 50% 0.626 4%

Pagefind's 0% zero-result rate is a defect rather than coverage. The query set includes zzzzqqq, which has no right answer; Pagefind returned /docs/support/log-files for it. Legacy and Orama correctly returned nothing.

Success@5 by query type — where the engines actually differ
Engine Exact title Head term Natural language Typo Ambiguous title Adversarial
Legacy 100% 81% 67% 42% 90% 50%
Pagefind 100% 56% 73% 25% 40% 50%
Orama 100% 75% 87% 58% 80% 50%

All three are perfect on exact page titles, so that column decides nothing. The differences live in the middle four. Orama wins natural language and typos by wide margins; legacy wins head terms and ambiguous titles, where 44 titles are shared by more than one page and the canonical one has to come first.

The overlay searches on every keystroke, so most of the time the panel is open it is showing results for a partial query. This is the metric closest to what the reader actually experiences, and Orama leads it by 14 points.

Evidence — speed

How fast does it feel?

Fast 4G with a 4× CPU penalty, which is roughly a mid-range Android on a good mobile connection. Medians of three consecutive runs; the spread across runs was under 80ms on every figure except Orama's cold start.

First result, and the cost of a keystroke
Engine Cold, empty cache Warm, same visit Return visit Keystroke p95
Legacy 673ms 276ms 232ms 221ms
Pagefind 2073ms 1092ms 260ms 1036ms
Orama 5714ms 256ms 201ms 228ms

Read the four columns as one story. Orama is the slowest to answer the very first search of a visit and the fastest at everything after it. Pagefind is the opposite of what its tiny index suggests: because it fetches index chunks per query, every keystroke costs a network round trip, and 1036ms per keystroke is the worst number in this table.

Legacy is unremarkable and consistent, which is why it passes everything.

Gates — pass or fail, set before the runs
Engine Cold ≤ 2000ms Warm ≤ 300ms Keystroke ≤ 250ms Wire ≤ 0.81MB
Legacy 673ms 276ms 221ms 0.35MB
Pagefind 2073ms 1092ms 1036ms 0.08MB
Orama 5714ms 256ms 228ms 0.66MB

Legacy's keystroke figure of 221ms and Orama's of 228ms both sit just under a 250ms gate, and the overlay's own 150ms debounce is inside both. Treat those two as equal. Pagefind's 1036ms is not close.

For whoever is choosing

What you gain and give up with each

Legacy

  • Passes all four performance gates
  • Best at rank one (58%) and best MRR (0.671)
  • Best on ambiguous titles (90%) — its hand-tuned field weights earn their keep
  • Weakest on misspellings after Pagefind (42%)
  • Keeps 645 lines of custom stemmer, synonyms and ranking
  • 8% of queries return nothing at all

Pagefind

  • 0.08MB on the wire, 0.11MB parsed — an eighth of Orama on the wire, a fiftieth once parsed
  • The only engine that can deep-link to a heading, not just a page
  • Cheapest by far for the readers who never search, and it already warms on page load
  • Relevance last by 16 to 18 points, and not fixable by configuration
  • 1036ms per keystroke; each one is a network fetch
  • Invents results for nonsense queries

Orama

  • Best Success@5 (78%) and best while typing (63%)
  • Best natural language (87%) and typos (58%) by wide margins
  • Fastest once loaded: 256ms warm, 201ms on a return visit
  • 5.7s first search on a cold cache — the one gate miss
  • 5.33MB parsed on every fresh page load, which caching cannot remove
  • No per-heading deep links without new chunking work

Pagefind's heading-level deep links are the one capability on this page that only one engine has. It is returning them on every single query today and the spike throws them away; wiring them up is the largest piece of unbuilt work in either spike. It would not move any number above, because these metrics score the page. It would change what landing on a 4,000-word page feels like.

Decision levers

What would change this recommendation

A cold first search must be under 2s on mobile
Orama is out at 5.7s, and no configuration closes a 3.7s gap. Then the choice is legacy against Pagefind, and legacy wins on every axis except payload. Practically: keep legacy.
Getting the right page at rank one matters more than having it on screen
Legacy leads Success@1 by 8 points and MRR by 0.045. If the reader habitually presses Enter on the first result rather than reading the list, legacy is genuinely better and Orama's win narrows to typos and natural language.
Someone will build Pagefind's sub-results
Pagefind gains a real capability neither other engine has, but its relevance stays at 60%. It changes what the best option is only if deep links matter more than finding the page at all.
Orama's index can be made substantially smaller
The recommendation becomes unambiguous. It has already gone 11.43MB to 5.33MB; BODY_LIMIT is still 4,000 characters and the stored excerpt copy could shrink further. Cutting the cold path is the highest-value work left on either spike.
Method and limits

How to read this, and what it does not tell you

  • All three run the same overlay. The search UI merged to main before either spike branched, so the only thing that differs between the three is the engine behind one interface. Production is the baseline for free.
  • Expected URLs were written before the runs and re-checked against the live page list; all 102 still resolve. 14 queries are recorded but unscored, because they exist to show how an engine degrades rather than to have a right answer.
  • There is no real query data, and there cannot be. The search is client-side and nothing reports what readers type, so the head-term queries are derived from the corpus two ways — term frequency across pages, and the site's own 26 top-level sections. Google Search Console is the one untapped source of real reader language, if anyone has access.
  • Both spikes were audited and fixed first. Orama was misconfigured in four ways, the worst of which silently cut its recall by a factor of sixty; searching variables matched 5 pages instead of 321. All four are fixed. Pagefind was already close to idiomatic, and its ranking parameters were already at their best values.
  • Pagefind's deficit was tested, not assumed. Removing every competing API and CLI page from its index's reach lifted it only to 61%. Content weighting will not close the gap.
  • Not measured: peak memory on a real low-end device, behaviour on flaky connections, and how any of this feels to an actual reader. The numbers here are a floor for the decision, not the whole of it.
